## Acceptance criteria

1. `MatchVerse` has a bounded `max_containers`. `MAX_GPU_CONTAINERS` is read at import from the env var `WWJD_MAX_GPU_CONTAINERS` (default `2`) and passed as `max_containers=MAX_GPU_CONTAINERS` in `@app.cls(...)`. A value that is not a decimal integer of at least 1 (after stripping whitespace) raises `ValueError` at import with a fixed message naming the env var, so a bad value fails the deploy instead of silently removing the cap. An empty or unset value means the default. Tests: the AST of the `@app.cls` decorator has `max_containers=MAX_GPU_CONTAINERS`; with the env unset the constant is `2`; `"3"` gives `3`; `"0"`, `"-1"`, `"abc"`, `"1.5"` raise `ValueError` on import. The cap is documented in the README.
2. Input over the token cap is rejected with `422` before any generation. `MAX_PROMPT_TOKENS = 4096` counts the tokens of the full prompt (`build_prompt(text)`, template included). The check lives in a pure helper `_tokenize_capped(tokenizer, prompt, max_tokens)`: it calls `tokenizer(prompt, return_tensors="pt")` once and returns the inputs when `inputs.input_ids.shape[1] <= max_tokens`, else `None` (plus the count, for logging; exact return shape is the implementer's choice, documented in its docstring). `_generate_verse` calls it after tokenizing and before `model.generate`; when over the cap it does not call `generate` and returns the structured result `{"error": "input_too_long"}` (no text, no counts, no output). It logs `[<id>] rejected: reason=input_too_long input_length=<chars> prompt_tokens=<n> max_prompt_tokens=<cap>` (metadata only). `handle_verse_request` maps that result to `422` with body exactly `{"error": ERROR_TOO_MANY_TOKENS, "id": <id>}`, `ERROR_TOO_MANY_TOKENS = "The 'text' field is too long for the model; select less text."`, and logs `[<id>] done: status=422 reason=input_too_long`. It must be checked before the generic `"error" in result` 502 branch; any other `"error"` value stays the `502` `match_error`. Tests with a fake tokenizer and fake model: exactly at the cap generates; one over the cap never calls `generate`, returns `{"error": "input_too_long"}`, and the user text is not in the log; `handle_verse_request` maps it to the `422` body without echoing the text; `{"error": "parse_failed"}` stays `502`.
3. Oversized request bodies are rejected without being parsed in full. `MAX_BODY_BYTES = 65536`. `verse_api` takes `request: Request` (starlette `Request`, which FastAPI passes raw) instead of `body: VerseRequest`. A pure async helper `read_limited_body(headers, chunks, max_bytes)` (names are the implementer's choice): if `Content-Length` is a valid integer above the cap, it rejects without reading the body; otherwise it reads `request.stream()` chunk by chunk and stops as soon as the running total exceeds the cap, without reading further. An oversized body returns `413` with body exactly `{"error": ERROR_BODY_TOO_LARGE, "id": <32 hex>}`, `ERROR_BODY_TOO_LARGE = "The request body must be at most 65536 bytes."`, built from the constant, and logs `[<id>] rejected: status=413 reason=body_too_large` plus the declared length or bytes read (no body content). The cap is checked before any JSON parsing and before any GPU call. A body within the cap is validated with `VerseRequest.model_validate_json(raw)`; a pydantic `ValidationError` (including invalid JSON) is re-raised as `fastapi.exceptions.RequestValidationError` with each error's `loc` prefixed by `"body"`, so the client still gets FastAPI's default `422` `{"detail": [...]}` as the README contract says. A valid body goes to `handle_verse_request(body.text, MatchVerse().match.remote.aio)` exactly as now. Tests: a `Content-Length` over the cap returns 413 and the stream is never iterated; a body without `Content-Length` (or with a lying smaller one) that streams past the cap returns 413 and stops reading at the first chunk that crosses it; a body of exactly `MAX_BODY_BYTES` is accepted; invalid JSON and `{}` raise the validation error path (tested with fastapi stubbed, as the existing wrapper tests do); a valid body still returns 200 via `.remote.aio`.
4. Why 64 KiB: a valid request is `{"text": ...}` with at most 4000 characters; the worst JSON encoding of one character is a `\uXXXX\uXXXX` surrogate pair (12 bytes), so 4000 characters fit in 48,000 bytes plus a few bytes of framing. 65536 leaves room for whitespace while bounding the bytes read to 64 KiB.
5. Why 4096 prompt tokens: Mistral-7B-Instruct-v0.2 has a 32,768 token context and `max_new_tokens=500`, so any prompt up to about 32,000 tokens would fit, but the cap is a cost bound, not a fit bound. The template (`build_prompt("")`, 1018 characters of English) is roughly 250 tokens. English and most text at 4000 characters is roughly 1000 to 1500 tokens, so 4096 accepts every realistic selection under the 4000 character limit, including denser scripts at about 1 token per character, while rejecting the byte-fallback worst case (about 4 tokens per character, about 16,000 tokens) that would make prefill and KV cache work about 4 times larger. Prompt plus generation stays under 4,600 tokens. These estimates are stated as estimates in the PR; the gated tokenizer cannot be run here.
6. Preserved behavior from #2, #3 and #5: `MatchVerse` with `@modal.enter` load-once; `verse_api` with no GPU, `@app.function` outermost, then `@modal.concurrent(max_inputs=20)`, then `@modal.fastapi_endpoint(method="POST", docs=True)`, awaiting `.remote.aio`; the 4000-character `422` with `{"error","id"}` and no echo; metadata-only logging, `WWJD_LOG_FULL_TEXT`, `request_id` passed and normalized, `_run_guarded` and `MatchVerseError`. The `input_too_long` result is returned normally from inside `_run_guarded` (it is not an exception). Existing tests keep every assertion; tests that call the raw `verse_api` with `VerseRequest(...)` change only their call shape to a fake request carrying the same JSON, because the signature changes.
7. README: the API contract gains rows for the `413` and the token `422`; the `{"detail": [...]}` row also covers invalid JSON; the architecture section says `verse_api` reads the raw body with a byte cap before validating it, and `MatchVerse` has `max_containers` (default 2, `WWJD_MAX_GPU_CONTAINERS`) and checks the token cap before generating; it says requests beyond the cap queue in Modal and may see the `303` or timeout responses; a "Cost limits" note lists the caps and recommends setting a spend limit in the Modal workspace settings (the run does not change Modal settings); the logging section lists the new reasons (`body_too_large`, `input_too_long`). `/docs` no longer shows the request schema, because the body is read by hand; say so.
8. The CI gate passes: `ruff check .`, `pytest`, `python -c "import wwjd_bot_modal; print(wwjd_bot_modal.app.name)"`.

## Risks

- FastAPI must see the `Request` annotation as the real class in the container, or it will treat `request` as a required query parameter and every call returns `422`. The guarded import is the riskiest step; no local FastAPI exists to prove it end to end. Mitigation: install the pinned `fastapi` and `starlette` from `requirements-api.txt` into a scratch venv (not the repo's dev requirements), mount the same handler with `magic_fastapi_app`-equivalent wiring (`FastAPI().add_api_route("/", raw_verse_api, methods=["POST"])`) and drive it with `fastapi.testclient.TestClient` in the live drive. Do not add fastapi to `requirements-dev.txt`.
- `request.stream()` after a partial read: stopping early is fine for the response; the remaining bytes are discarded by the server.
- The `413` replaces what would have been a FastAPI 422 for huge bodies. Content-type is no longer checked by FastAPI; `model_validate_json` accepts the JSON bytes regardless of `Content-Type`. Note this in the README contract.
- Requests beyond 2 GPU containers queue in Modal; under load users see longer waits, `303`s, or timeouts. Documented, by the user's decision.
- `MAX_GPU_CONTAINERS` is read at import, also inside containers, where the env var is not set; the deploy-time value is what Modal registers, as with `WWJD_APP_NAME`.

Not done on purpose: authentication (user decision), changing Modal settings, rate limiting per client, the prompt and template issues tracked in #4.
